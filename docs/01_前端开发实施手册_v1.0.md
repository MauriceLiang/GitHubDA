## 0. 强制约定：不得自行修改

1. **技术边界**：Streamlit 仅通过 `frontend/api/client.py` 使用 HTTP/JSON 调用 FastAPI；禁止在前端直接导入后端 ORM、数据库连接、`services`、直接调用 GitHub REST API 或保存 GitHub Token。
2. **API 版本**：统一 `/api/v1`；请求/响应、错误码、状态机、数据时间、分页、字段命名，以 `03_API接口契约_v1.0.md` 为唯一依据。
3. **Mock 策略**：前端通过本地符合契约的 JSON fixture 开发。开启真实模式后不能静默回退至 Mock；必须在界面明确展示“演示模式”。
4. **数据诚实性**：null 是未知，不是 0；API 尚未提供历史数据时不得画假趋势。指标必须可追溯到采集时间和统计范围。
5. **研究口径**：固定研究样本 `research` 与用户个人库 `library` 严格分离。用户新增项目不得改变固定研究结果。
6. **主题**：默认 GitHub Developer Workspace Dark：`#0D1117` 背景，`#161B22` 面板，`#E6EDF3` 字体，`#58A6FF` 主交互。提供官方可用的 Light 切换方式；禁止用脆弱 CSS 伪造 Streamlit 原生主题切换。
7. **产品定位**：开发者开源项目评估工具，不是 GitHub 复制品、官方应用、质量/安全权威评级系统。
8. **MVP 安全**：API 内部密钥仅保存在 Streamlit 服务端环境变量；不要呈现在浏览器、Markdown、日志、错误栈中。应用默认供本地单用户使用。
9. **分阶段交付**：每个阶段先验收、再继续；不得在某个页面尚未连通契约时扩建额外页面。

## 1. 交付范围、页面清单和目标体验

## 2. 前端技术选型与文件权限

- Python 3.12、Streamlit（锁定双方测试过的同一个具体版本）、Plotly、Pandas（仅在展示层做轻量 DataFrame 适配）、HTTPX（同步客户端）、Pydantic v2（客户端数据模型，或由 OpenAPI 生成的兼容模型）、Pytest、respx（模拟 HTTPX）。
- UI 不需 Vue/React/Tauri，也不引入持久化的前端数据库。
- Streamlit 的 Session State 仅存页面交互状态，例如当前筛选器、仓库选择与当前查看任务；不能用作唯一任务持久化。
- HTTP 客户端使用 `httpx.Client` 连接池、超时策略、统一异常映射；重试仅对安全 GET 且符合幂等策略的请求进行，禁止对 POST 添加仓库盲目重试。

### 4.2 请求的规范行为

- 从 `API_BASE_URL` 读取服务地址，默认本地 `http://127.0.0.1:8000`；从服务端环境变量读取 `INTERNAL_API_KEY`，加 `X-Internal-Api-Key`；绝不将密钥写入 UI 文本或 URL query。
- 请求超时：本地 FastAPI 读接口初始建议连接 3s、读取 15s，GitHub 搜索经后端代理可能超过 15s，实际值与后端协商；任务执行不靠页面请求等待。
- 根据 HTTP 状态与 `error.code` 显示用户能理解的文案；展示 `request_id` 便于排查，不展示原始栈或密钥。
- 204 不解析 JSON；CSV 响应按字节交给下载按钮。200/201/202 读取 envelope `data`。
- 对重复点击添加/重试生成一次性 `Idempotency-Key`，只为一个用户操作保留固定值，网络重发时复用该 key。
- 对 GET 使用短期 `st.cache_data` 时将 scope/dataset_id/筛选条件和数据版本或刷新令牌作为缓存 key；搜索不能无限缓存旧的 GitHub 结果。
- 后端不可用、GitHub 限流、仓库不存在分开展示。后台任务完成后刷新数据缓存并重新拉取真实分析结果。

### 4.3 前端 DTO 和缺失值边界

`RepositoryPreview`, `RepositorySummary`, `Task`, `Analysis`, `SourceMetadata`, `Overview`, `Comparison`, `ErrorResponse` 一律与接口文档字段完全一致。`stars: int | None`、`progress_percent: float | None`、`commits_90d: int | None` 等不可擅自改成强制 int，不能 `value or 0`。

## 5. 按页面实施的具体规则

### 5.1 Dashboard 数据概览

- 顶部 `Dashboard / 研究样本 vX` 面包屑，右侧数据期次和“刷新数据”入口。
- 筛选栏：`scope` 切换 `research/library`；研究范围需选择 `dataset_id`，个人库不得携带研究 dataset_id；语言筛选。
- 四个 KPI：仓库成员数、已分析数、Star 中位数、90 天内有推送的数量；KPI 单位和计算范围对齐。
- 第一行：主要语言样本数柱状图 + Star 分布直方图/区间图；第二行：研究样本状态与最近采集说明。固定样本 400 与实际有效样本 365 必须分别展示。
- 空态：没有数据时显示“尚无可分析仓库”，引导前往 Explore；API 离线允许显示缓存但必须注明来源和时间。
- 状态来源：GET `/datasets`、GET `/overview`。

**验收**：切换 scope 时绝不混合数据，语言筛选后所有 KPI/图表一致更新；缺失值不造成图表报错；`sample_size` 与 `valid_sample_size` 不混用。

### 5.2 Explore 仓库发现（核心）

- 顶部以搜索为焦点。`st.form` 文本输入 + 搜索按钮；用户未提交时不发起新 API 请求。
- 支持普通关键词搜索、语言过滤、最低 Star、排序及分页。粘贴 GitHub URL 或 `owner/repo` 时使用 Resolve 路径，不当作普通关键词搜索。
- 结果行布局：仓库名（外链 GitHub）、描述（最多 2–3 行）、语言色点、Star、Fork、最近更新时间、是否已加入库、添加按钮。长名称不得挤压右侧按钮。
- 点击添加：先在 UI 防重复，提交 `POST /library/repositories` 后根据 `membership_created`、`task_id` 和 `analysis_status` 展示状态；不可凭按钮点击即假定任务成功。
- 限流：显示 `retry_after_seconds`，保留用户条件，允许稍后重试；绝不切换到虚构的搜索结果。
- 搜索返回 `incomplete_results` 时展示“GitHub 搜索结果可能不完整”；超出可见 1,000 项时关闭下一页。

**验收**：搜索可返回真实列表；相同仓库重复添加不造成两条记录；输入错误 URL 受控失败；搜索结果不误当成已分析数据；Mock 模式显式警示。

### 5.3 Library 我的分析库（核心）

- 表格列：复选、仓库、语言、Star、数据状态、分析状态、最近成功采集时间、操作；支持排序/筛选。
- 每行操作：查看详情、基础刷新、深度采集、移除。移除只影响“我的分析库”成员，确认弹窗须解释不删除原始/研究数据。
- 选择 2–5 个仓库后点击“加入对比”，使用 `st.session_state` 保存 IDs 并跳转 Compare。
- `Task` 的 queued/running/succeeded/partial/failed 与 `analysis_status` 分开处理；`data_status=stale` 即使 analysis completed 仍要显示“数据已过期”。
- 任务轮询建议使用 `@st.fragment(run_every="3s")` 只刷新状态区；任务完成停止不必要的重复请求。若列表大，应分页。

**验收**：关闭当前页面、切换导航后，任务仍在后端执行；删除成员并不删除仓库快照；队列状态从服务器恢复，不依赖 session_state。

### 5.4 Repository 单仓库详情

- 页面主信息：仓库名、主要语言、简介、GitHub 外链、采集时间、数据新鲜度、基础/深度状态。
- 5 个 Tab：概览、维护活动、社区协作、历史趋势、指标说明。
- 概览：Star/Fork、创建时间、最近推送间隔及许可证提示；活动 Tab：90 天 Commit/一年 Release；社区 Tab：Issue/PR；若深度数据缺失，展示显式“开始深度分析”。
- 历史趋势用 `/series?metric=stars|forks`；1 个点不能生成增长曲线；2 个点只画实际观测线段，展示“观测点少”。
- 数据来源折叠区展示 GitHub REST API、采集时间、窗口与 `coverage`，直接显示 limitations。
- 可切换具体仓库，但不能把仓库 A 的图表缓存误用到仓库 B。

**验收**：只有基础数据也可正常展示；0 与 null 视觉不同；无真实历史数据时图表为空。

### 5.5 Comparison 多仓库对比

- 从 Analysis Library 选择 2–5 个仓库，顺序稳定，用 API `POST /comparisons` 获得结果。
- 表格并排：Star、Fork、仓库年龄、最近推送间隔、90 天 Commit（仅深度数据齐全时）、一年 Release 等；每个数据列标注采集时间。
- 图表只能比较同一指标、同一单位、同一观测窗口；采集相差超过 24h 时警告，不自动强行归一化掩盖差异。
- 不输出“综合安全分”“绝对质量分”，尤其禁止以 Star 排名代表选型结论；不同用途项目展示弱可比性警示。
- 比较 API 遇缺少基础数据的仓库要提示刷新；不能前端伪造一个全零指标对象来继续。

**验收**：2、5 个仓库均正常排版；第 6 个选择被阻止；跨语言/跨类型比较有解释；导出保持图表同源数据。

### 5.6 Research 数据研究中心（课程重点）

- 只接受 `type=research` 的数据集，展示样本版本、筛选规则、冻结时间、有效样本数量。
- 五个视图：描述性统计、特征分布、分组比较、Spearman 相关性、数据质量报告。
- 描述性统计展示 `count / mean / median / std`，偏态分布强调 median 和分位数。
- 相关性视图显示系数、p 值、有效样本 n；统计检验不满足条件时必须显示“无法计算/样本不足”。
- 数据质量视图标注缺失项、排除原因、样本总数与可分析数，突出科学性。
- 图表旁有可读解释与局限：样本不能代表整个 GitHub 语言市场份额。

**验收**：新增个人仓库前后，固定研究样本统计不变；任意一项统计量有样本版本和时间依据。

### 5.7 Operations 数据与任务管理

- 顶部卡片：API 状态、Worker 心跳、排队/运行/失败数量、最近成功同步、GitHub 已知限流快照。
- 任务表支持 status、repository_id 筛选和分页；行内展示 Task ID（可复制）、开始时间、阶段、失败码、重试操作。
- 仅 `failed` 或 `partial` 状态显示可点击“重试”；重试成功显示新的 task_id，不覆盖旧任务记录。
- 无精确任务进度时使用不定进度动画，不制造 47% 等虚假数字。
- API 限流只显示后端真实观测值，未知时写“未获取配额数据”。

**验收**：Worker 离线、限流、部分成功、完全失败四种状态都可以从 API fixture 复现且正确反馈。

### F2–F6 实施细则

## 7. 前后端协作协议（前端必读）

**里程碑 A：API 契约锁定**：双方对字段/状态/分页/错误码确认；后端先提供 OpenAPI 与 fixture；前端从 fixture 实现组件。

**里程碑 B：首条真实链路**：后端具备 GitHub 搜索、Resolve、添加、后台 Worker、任务查询和基础分析；前端切换 `MOCK_MODE=false`，联调一次完整过程。

**里程碑 C：统计研究**：后端开放 `datasets`, `overview`, `research/*`, `comparisons`；前端只消费 API 响应并展示科学性标注。

**里程碑 D：异常与交付**：限流、网络异常、重复添加、SQLite 重试、导出、Worker 离线均可复现；录制测试过程。

- 不共享运行中的全局 `st.session_state` 或后端 ORM 对象；只通过 API 契约通信。
- 对契约差异开 Issue，附请求、真实响应、预期字段、对应契约节；后端不得无通知改字段。
- PR 建议分 `feat/frontend-shell`, `feat/frontend-explore`, `feat/frontend-analysis` 等；前端负责人只改前端目录，保护主分支。
