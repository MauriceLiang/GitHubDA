## 1. 为什么从模块化单体调整为 HTTP 前后端分离

课程项目原本可用 Streamlit + Python Services 直接访问 SQLite，但现在明确由两位开发者并行承担 UI 和数据处理。选择在同一代码仓库内使用独立 Streamlit 服务、FastAPI 服务、Worker 进程，建立**稳定明确、可以 Mock 的 API 契约**，避免两人同时修改 Service/ORM 或靠 import 耦合。

这属于小型项目的轻量分层，不采用分布式微服务、消息中间件或复杂前端 SPA。

```text
开发者/教师浏览器 (HTTP 8501)
         │
         ▼
Streamlit 前端进程 [frontend/]
7 主页面 + 仓库详情 + Plotly
         │  仅服务端 HTTP/JSON：X-Internal-Api-Key
         ▼
FastAPI HTTP 进程 (127.0.0.1:8000) [backend/app/api/]
路由 + DTO + 参数校验 + Services
         │                    │
         ├──> SQLite <────────┤  独立 Worker [backend/app/worker/]
         │    仓库/成员/任务/快照/结果         │
         └──> GitHub Search/Resolve            └──> GitHub API
                                                 ↓
                                           原始数据归档
                                                 ↓
                                         Pandas 清洗/特征工程
                                                 ↓
                                          SciPy 统计 + SQLite
```

## 2. 关键架构决策记录（ADR）

| 编号 | 已定决策 | 理由 | 禁止事项 |
|---|---|---|---|
| ADR-01 | Streamlit 负责所有用户界面 | Python 快速可视化，符合课程 | 额外引入 Vue/React |
| ADR-02 | FastAPI 统一 API | 前后端独立开发与联调 | UI 直接调用 ORM/Service |
| ADR-03 | REST JSON `/api/v1` + Pydantic DTO | 契约明确，可自动测试 | 临时自定义字段名 |
| ADR-04 | SQLite + SQLAlchemy + Alembic | 部署简单、可复现 | 第一版引入 PostgreSQL、Redis |
| ADR-05 | 独立单 Worker + APScheduler 3.x | Streamlit rerun 不影响采集 | 在 Streamlit 线程内永久采集 |
| ADR-06 | GitHub REST API | 数据来源透明可追溯 | 随意爬页面或伪造增长历史 |
| ADR-07 | 固定研究样本与个人库成员隔离 | 统计研究可重复 | 用户新增后修改冻结样本 |
| ADR-08 | 基础分析默认、深度分析按需 | 节流，降低数据处理成本 | 默认下载所有 Commit/Issue/PR |
| ADR-09 | Dark 默认 + GitHub 蓝色强调 | 与开发者工具定位一致 | 恢复旧深青绿色主题 |
| ADR-10 | 无多用户登录（首版） | 控制结课范围 | 没鉴权就公开多人工作区 |

## 3. 两位开发者责任和代码所有权

| 职责项 | 前端 | 后端 |
|---|---:|---:|
| Streamlit 七主页面、组件、UI/UX | 负责 | 不修改 |
| HTTP API 客户端、DTO 解析、Mock 模式 | 负责 | 提供合同/fixture |
| Plotly 图表、页面数据展示 | 负责 | 提供正确指标和元数据 |
| FastAPI 路由、Pydantic Schema、OpenAPI | 消费 | 负责 |
| GitHub 采集与分页限流 | 不直接调用 | 负责 |
| SQLite/Alembic、仓库/样本/任务数据模型 | 不直接操作 | 负责 |
| Worker、调度、数据归档、异常恢复 | 显示状态 | 负责 |
| Pandas/SciPy 指标计算、清洗、研究统计 | 只展示 | 负责 |
| API 契约变更评审和测试 | 共同确认 | 共同确认 |

前端权限目录：`frontend/`, `tests/frontend/`。后端权限目录：`backend/`, `tests/backend/`, `migrations/`, `scripts/`。共用 `contracts/`, `fixtures/`, `README.md`, `pyproject.toml` 等文件修改需双方 PR review。

## 4. 共同开发顺序与里程碑

| 同步里程碑 | 前端执行 | 后端执行 | 联调门槛 |
|---|---|---|---|
| M0：合同冻结 | F0 骨架、F1 Mock+DTO | B0 DTO/路由/OpenAPI/DB | 字段、枚举、错误、分页、固定 fixture 一致 |
| M1：搜索添加基础闭环 | F2 Explore、Library | B1 GitHub 搜索，B2 后台最小任务 | 搜索→添加→排队→分析完成→仓库详情 |
| M2：单项目分析/比较 | F3 仓库详情与比较 | B3 清洗/历史，B4 深度采集 | null/partial/时间窗口语义一致 |
| M3：课程研究与概览 | F4 Dashboard/Research | B5 冻结样本/描述统计/质量报告 | 固定研究样本有实际证据，研究与用户库隔离 |
| M4：任务与完善 | F5 Operations、导出、主题验收 | B6 调度、心跳、恢复 | 限流、超时、Worker 离线、缓存旧数据均可复现 |
| M5：最终交付 | F6 视觉/体验/演示 | B7 契约/安全/性能/研究复现 | 完整系统和测试报告可交付 |

**工作并行原则**：前端从第一天即可在 Mock fixture 下完成页面；后端从第一天生成 Pydantic/OpenAPI 和数据库迁移；M1 再接第一条真实 API 链路，避免等待对方完成所有功能。

## 5. Git 与 PR 管理建议

- `main` 受保护，不直推；功能分支以 `feat/frontend-*`, `feat/backend-*`, `docs/contract-*`, `fix/integration-*` 命名。
- UI 开发者从 `main` 分支开始，不改 API 字段；后端开发者按锁定契约实现字段。
- 禁止同一 PR 改动大量非职责文件；API 变更提交专门的 `docs/contract-*` PR，同时修订文档、DTO 和 fixture。
- 每个里程碑 PR 必须包含测试、演示截图（前端）/真实输出片段（后端）、变更范围和验收结果。
- 契约版本为 v1：只能兼容性地添加可选字段；破坏性修改需要双方书面确认、必要时提升 `/api/v2`。

## 6. 本地启动与配置约定

使用 Python 3.12 的虚拟环境。具体依赖由两端实现后固定 `pyproject.toml`/lock。后端先初始化 SQLite 迁移，然后分别在三个终端启动：

```bash
# 终端 1：FastAPI，仅本机
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000

# 终端 2：独立 Worker，执行 SQLite 队列任务
python -m backend.app.worker.main

# 终端 3：Streamlit Web
python -m streamlit run frontend/app.py --server.port 8501
```

以上命令是**计划的模块路径约定**，在源码完成以前无法实际执行；工程结构必须与路径保持一致。

建议 `.env.example`（无真实密钥）：

```dotenv
API_BASE_URL=http://127.0.0.1:8000
INTERNAL_API_KEY=change-this-in-local-environment
GITHUB_TOKEN=replace-with-token-in-local-environment
DATABASE_URL=sqlite:///./data/app.db
RAW_DATA_DIR=./data/raw
MOCK_MODE=false
WORKER_POLL_SECONDS=3
BASE_REFRESH_HOURS=24
```

- Streamlit 服务端持有 `INTERNAL_API_KEY`；浏览器不直接连接 FastAPI，也不应出现 Key。
- FastAPI 不应绑定公网接口；若服务器部署，通过反代登录保护 Streamlit，并限制 API 仅本地可见。
- SQLite 工作目录应固定为项目根下 `data/` 的绝对解析路径，避免从不同 `cwd` 启动后创建两个不同数据库。

## 7. 统一 API 行为（重要）

- `/api/v1` JSON 成功响应：`{"data":…, "meta":{"request_id":…,"generated_at":"…Z"}}`；列表再加 pagination；错误 `{"error":{"code":…,"message":…,"details":…},"request_id":…}`。
- 204 删除不带响应体；CSV 导出返回真实 CSV，不包装 JSON。
- `repository_id` 为 GitHub ID；`full_name` 可能改名。`task_id` 为 UUID。
- 任务 `queued/running/succeeded/partial/failed/cancelled`；阶段 `collecting/cleaning/analyzing/persisting`；仓库 `analysis_status` 与 `data_status` 是独立状态。
- `null` 是未知/未收集，0 是已确认值；已存的时间序列不允许伪造回填。
- POST 添加或刷新立即响应（201/200/202），任务在 Worker 执行；前端轮询 `/tasks/{id}`，不要同步等待外部 GitHub 大量分页。
- GitHub search 结果的总数受其搜索机制限制，不能当作全平台项目数量。研究样本报告必须显示 dataset_id、规则版本与有效样本数。

## 8. 契约 fixture 使用方式

交付包的 `fixtures/` 提供格式示意 JSON（模拟数据，不是实时数据）。前端 Mock 根据它们渲染；后端可以将其作为 contract snapshot 的基线，但业务测试应另外构造边界条件。

必须通过的横向流程：

- 搜索 `psf/requests`：API 搜索/Resolve 可正常响应。
- 首次添加：返回成员关系和 task_id；后端实际采集后能查到分析结果。
- 重复添加：不新增成员；同一运行中的同深度任务复用。
- 深度数据缺失：API null + not_collected；UI 显示缺失和深度采集按钮。
- 固定研究样本：新加用户库成员后，research 统计样本数量不变。
- GitHub 限流/离线：保留可信旧数据，界面不显示假实时。
- CSV：UTF-8、元数据、合理列、避免公式注入。
