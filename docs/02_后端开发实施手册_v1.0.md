# GitHub 开源项目数据分析与技术选型辅助系统
# 后端开发实施手册 v1.0（FastAPI / Worker / 数据分析开发者执行版）

> 日期：2026-10-13 | 状态：开发规划，所有端点均为待实现。  
> 负责：后端开发者（FastAPI、GitHub REST API 客户端、SQLite、Worker、Pandas/SciPy、数据质量及后端测试）。  
> 唯一接口约定：`03_API接口契约_v1.0.md`。  
> 用户场景：搜索 GitHub 仓库 → 添加分析库 → 数据拉取和清洗 → 分析 → 可视化。  
> 总体约束：课程《Python 编程与数据分析》，优先形成可复现的真实分析链路，不为了微服务化增加 Redis/RabbitMQ/Celery。

## 0. 不可改变的系统边界

1. **后端类型**：FastAPI + Pydantic v2，使用 `APIRouter` 分组，暴露 `/api/v1`；Streamlit 仅通过 HTTP 访问后端。FastAPI 自带 `/openapi.json`，实际 schema 必须与接口文档一致。
2. **后台进程**：独立 Worker 与 FastAPI 共用应用服务/数据库代码；Streamlit 不执行长任务，FastAPI 路由不得同步遍历仓库完整事件历史。MVP 单 Worker 串行处理。
3. **存储层**：SQLite + SQLAlchemy 2.x + Alembic。多线程/多进程使用各自独立 Session；开启 WAL、busy timeout、foreign_keys。
4. **GitHub 数据真实性**：只用官方 REST API 真实数据；`updated_at` 不等于最近代码推送，`open_issues_count` 可能含 PR；缺失值不得默认为 0。
5. **研究样本**：固定研究样本与个人库采用不同 dataset membership；用户添加仓库不改变 research 的成员构成。
6. **幂等性**：GitHub repository ID 全局唯一；任务 UUID 独立；重复添加同项目不能重复创建个人库成员或并行相同任务。
7. **安全**：不采集私有仓库；用户输入 URL 只允许 GitHub 仓库格式，禁止直接请求用户传入的任意主机；Token/内部 Key 不进日志、数据库公开字段或 Git。
8. **稳定性**：Worker 崩溃后可重新认领超时任务；采集失败保留最后成功快照与分析结果，错误日志有可查 request ID。
9. **统计解释**：本产品辅助选型，不提供“绝对代码质量/安全得分”；相关性不证明因果；所有统计有样本版本、分母、时间窗口和覆盖信息。
10. **接口契约优先**：如本手册与 API 文档有冲突，以 `03_API接口契约_v1.0.md` 为准，必须走变更流程，不得偷偷修改返回字段。

## 3. SQLite 数据库详细结构（迁移必须实现）

统一约定：数据库中时间全部 UTC（建议存 ISO 8601 字符串或 SQLite 支持的约定格式，在 ORM 边界规范化）；API 序列化固定 `YYYY-MM-DDTHH:mm:ssZ`；int64 仓库 ID 不得浮点化。

### 3.1 `repositories`：仓库身份与最新档案

字段：`repository_id INTEGER PRIMARY KEY`（GitHub 原生 ID）、`full_name TEXT NOT NULL UNIQUE`、`html_url TEXT NOT NULL`、`description TEXT NULL`、`language TEXT NULL`、`topics_json TEXT NULL`、`license_spdx TEXT NULL`、`created_at DATETIME NULL`、`pushed_at DATETIME NULL`、`github_updated_at DATETIME NULL`、`archived BOOLEAN NOT NULL DEFAULT 0`、`is_fork BOOLEAN NOT NULL DEFAULT 0`、`size_kb INTEGER NULL`、`first_seen_at DATETIME NOT NULL`、`last_seen_at DATETIME NOT NULL`。

- GitHub 仓库可能改名：以 repository_id 为准，更新 full_name；既有成员和历史快照仍关联 ID。
- `repositories` 保存档案字段；展示 Star/Fork 的可靠数值来源应是最新成功 `repository_snapshots`，避免部分更新导致不一致。

### 3.2 `repository_snapshots`：追加式仓库指标快照

字段：`id INTEGER PRIMARY KEY`、`repository_id FK`、`collected_at DATETIME NOT NULL`、`stars INTEGER NULL`、`forks INTEGER NULL`、`open_issues_and_pr_count INTEGER NULL`、`pushed_at DATETIME NULL`、`github_updated_at DATETIME NULL`、`response_etag TEXT NULL`、`source_http_status INTEGER NOT NULL`、`source_archive_path TEXT NULL`、`valid BOOLEAN DEFAULT 1`；索引 `(repository_id,collected_at DESC)`。

- 只有经过验证的有效响应/有效数据生成指标快照；HTTP 304 表示源未变，更合适记录在同步日志中，并更新检查时间，不能伪造新的观测数值；若需要表现无变化日期，应在算法说明中以已知观测为界，禁止冒充新采集的 Star 计数。
- 日粒度趋势选当日最后一次**成功、有效**观测；同日多次不重复累加。
- 旧快照永不因用户移除“我的分析库”而删除。

### 3.3 `datasets` 与 `dataset_repositories`

`datasets`: `dataset_id TEXT PRIMARY KEY`、`name`、`type ENUM(research,library,featured)`、`rules_version NULL`、`frozen_at NULL`、`created_at`、`description`、`source_metadata_json`。

`dataset_repositories`: `dataset_id FK`、`repository_id FK`、`added_at`、`selection_tier NULL`、`inclusion_reason NULL`、`exclusion_status NULL`、`selection_source NULL`；复合 UNIQUE `(dataset_id,repository_id)`。

- 初始 `library-default` 唯一共享个人库；`research-2026-v1` 为固定样本，`featured-default` 为首页精选；同仓库可属于多个集合。
- `research` 一旦冻结，不允许普通添加仓库接口修改成员。更改规则应创建新 dataset_id 和版本，不覆盖历史成员。
- 记录试采样查询、候选集合、语言/Star 层级、随机种子和排除原因到 `sampling_runs` 或 `source_metadata_json`；推荐专门有 `sampling_runs` 表便于复现，详见 3.7。

### 3.4 `collection_tasks`：持久化任务队列

字段：`task_id TEXT PRIMARY KEY(UUID)`、`repository_id FK`、`type TEXT`、`depth ENUM(basic,deep)`、`status ENUM(queued,running,succeeded,partial,failed,cancelled)`、`phase ENUM(collecting,cleaning,analyzing,persisting) NULL`、`progress_percent REAL NULL`、`message TEXT NULL`、`attempt INTEGER DEFAULT 0`、`retry_of TEXT NULL`、`idempotency_key TEXT NULL`、`created_at`、`started_at NULL`、`heartbeat_at NULL`、`finished_at NULL`、`error_code NULL`、`error_message NULL`、`lease_owner TEXT NULL`、`lease_until NULL`。

索引：`(status,created_at)`, `(repository_id,status)`, UNIQUE 非空 `idempotency_key` 作用域要包含操作类型/客户端来源，24 小时内不能产生不同结果。

- 待处理任务 `queued`；领取后 `running`；执行成功 `succeeded`；可用基础指标但某深度模块失败 `partial`；不可用 `failed`。
- `analysis_status` 是面向仓库的派生值，不是 collection_tasks.status 的同义词。
- `progress_percent` 仅有可计数子任务时设置，例如 2/4 个独立模块，未知时 NULL。
- 相同仓库运行中的重复 `basic`/`deep` 请求只复用已有任务；deep 可覆盖 basic 的数据需求，必须定义优先规则，初版宁可串行排队也不要同仓库并发。
- `retry` 总是创建新 task_id 并保留旧失败任务记录。

### 3.5 `repository_activity_windows`

字段：`id`、`repository_id FK`、`depth`、`window_start`、`window_end`、`commits_count NULL`、`issues_opened_count NULL`、`issues_closed_count NULL`、`pulls_opened_count NULL`、`pulls_merged_count NULL`、`releases_count NULL`、`coverage ENUM(complete,partial,not_collected)`、`collected_at`、`details_json`、`source_archive_path NULL`。UNIQUE `(repository_id,depth,window_start,window_end,collected_at)` 或等效版本键。

明确 `coverage`：分页未完整、超时/限流中止、上游响应不完整时只能标为 partial。未请求的项为 not_collected，不能记成 0。表中深度字段各自可追加 `*_coverage` 或 details_json 模块明细，不强行用统一 coverage 掩盖某一模块缺失。

### 3.6 `analysis_results`、`collection_logs`

`analysis_results`: `result_id`、`repository_id NULL`、`dataset_id NULL`、`analysis_kind`、`metric_version`、`window_start NULL`、`window_end NULL`、`source_collected_at`、`calculated_at`、`coverage`、`metrics_json`、`limitations_json`、`valid_sample_size NULL`。分析范围以 repo 或 dataset 标明；必须可重复计算。

`collection_logs`: `id`、`request_id`、`task_id NULL`、`repository_id NULL`、`event_type`、`source_endpoint`、`http_status NULL`、`occurred_at`、`retry_after_seconds NULL`、`message_redacted`；禁止记录 Authorization 原始头。

### 3.7 可选但推荐：`sampling_runs`、`worker_status`、`request_idempotency`

- `sampling_runs`: `run_id`, `dataset_id`, `rules_json`, `query_json`, `random_seed`, `candidate_count`, `accepted_count`, `rejection_counts_json`, `started_at`, `finished_at`；科学复现必需。
- `worker_status`: `worker_id`, `last_heartbeat_at`, `started_at`, `version`；用于 UI 服务状态与 Worker 超时恢复。
- `request_idempotency`: `key`, `operation`, `created_at`, `expires_at`, `response_json`, `status_code`；跨 HTTP 重试 24 小时响应复用。

### 3.8 事务与性能要求

- SQLite 设置 `PRAGMA journal_mode=WAL`, `PRAGMA foreign_keys=ON`, `busy_timeout`（如 5000ms），写事务尽量短，不能持有写锁调用外部 API。
- `Session` 按 HTTP 请求/Worker 任务单元创建并关闭；不可将一个 Session 在多个线程/进程共享。
- 所有查询分页；`stars` 分布统计与研究分析可以在 Pandas 中基于限定结果执行，样本约 400 不需要引入大数据引擎。
- 使用 Alembic 创建初始迁移、建立索引、提供从空库升级命令和可重复的导入脚本；不能用手工粘贴 SQL 改生产库。

## 4. GitHub REST API 客户端和真实数据采集

### 4.1 必须封装的方法

`search_repositories(q, language, stars_min, sort, order, page, per_page)`、`get_repository(full_name)`、`get_repository_by_id(repository_id)`（若实际端点适用）、`list_commits(full_name, since, until)`、`list_issues(full_name, since, state)`、`list_pulls(full_name, state)`、`list_releases(full_name)`。

- 官方入口 `https://api.github.com` 固定在服务端配置中；主域/协议不可由用户控制。
- GitHub 请求使用 `Accept: application/vnd.github+json`、合适的 API Version 头（若使用固定 API 版本）、Bearer Token（如配置）。
- 查询结束时读取 rate-limit headers，缓存核心限额和重置时间到内存或 DB；`GET /system/status` 只读缓存，不额外刷 GitHub 配额。
- 搜索 `per_page≤100`、GitHub search 单查询结果最多可查看 1,000 条，`incomplete_results` 显式透出。禁止前端拼接任意高权限 GitHub 查询。
- 只把合法查询限定到 `language/stars/sort/order` 白名单。对于 URL Resolve，使用安全 parser 解析 GitHub 官方域名 + owner/repo，不接受任意主机、userinfo、端口、任意后缀路径（防 SSRF）。

### 4.2 限流、分页与稳定性

- 对 `403/429` 结合 `Retry-After`、`X-RateLimit-Remaining`、`X-RateLimit-Reset` 和官方最佳实践决定是否等待。不要遇到 secondary limit 后立即无限重试；设置全局并发=1、搜索节流与最大重试次数。
- 5xx 和网络短暂错误按有上限的指数退避；404 公共仓库不可见返回业务 404，不重试；401 Token 配置错误不可无限重试。
- 采用 GitHub 官方 `Link` header 翻页，最大页数与窗口显式限定；分页中断后标记数据 `partial`，不记完成。
- GitHub 条件请求 ETag 使用持久化或缓存策略；304 保留已存在快照，更新“上次检查时间”，不能把 304 当首次成功抓取。
- 记录请求来源时间 UTC、目标仓库 ID、GitHub API 响应 status、采集覆盖情况。

### 4.3 需要额外谨慎的字段

- `stars`：GitHub `stargazers_count`，观察时点值，不代表真实使用者数量。
- `forks`：`forks_count`，不是贡献者人数。
- `pushed_at`：Git 推送时间代理指标，不是最新 release、Issue 活动或代码质量。
- `updated_at`：仓库元数据更新时间，不等于最新代码推送。
- `open_issues_count`：包含开放 PR，不是纯 Issue 总数；必须通过 Issue API 的 `pull_request` 字段区分或另行统计。
- `languages`：`language` 是仓库主要语言，不能推断该仓库只有这一种语言。
- Releases：有项目使用 Git Tag 而不创建 GitHub Releases；零 Release 只能解释为“未观察到 GitHub Release”。
- Commit：默认分支/窗口/合并策略会影响数量；如果 API 总量无法完整获取，不声称全量。

## 5. 数据处理管线（按顺序，不得跳过）

```text
搜索/解析 -> 验证仓库身份 -> 入队任务 -> 读取 GitHub 响应
             -> 原始 JSON 归档 -> Schema 校验/去重/标准化
             -> 数据质量报告 -> SQLite 快照与活动指标
             -> Pandas 特征计算 -> SciPy 统计（研究集合）
             -> 可解释结果与来源元信息 -> 更新 task 状态
```

### 5.1 原始数据归档

- 建议 `data/raw/{repository_id}/{UTC_date}/{task_id}/{type}.json.gz`；保留 GitHub API 原始业务字段和独立 metadata（source URL path、查询参数白名单、采集时间、HTTP 状态、ETag），禁止写 Authorization、URL token。
- 归档写入使用临时文件 + 原子 rename；保存路径相对 project data dir，禁止任意路径穿越。
- 原始数据可用于复验清洗逻辑；研究者提交时可另提供经过授权且体量合适的样本 CSV。

### 5.2 数据清洗规范

| 操作 | 明确规则 |
|---|---|
| 字段提取 | 映射 `id→repository_id`、`stargazers_count→stars`、`forks_count→forks`、timestamp 日期字段等 |
| 主键去重 | 以仓库 GitHub `id` 去重；重命名更新 `full_name` 而非新建仓库 |
| 日期标准化 | 解析 GitHub ISO 时间，转 UTC；解析失败为 null 且记录质量报告 |
| 类型处理 | 数量应为非负整数；不要将 `null`、空字符串转 0 |
| 缺失处理 | `description`、`language`、`license` 等可缺失；对分析关键字段分类处理 |
| 资源仓库 | 根据 Topic、README/描述的可审计规则标记教程/书籍/资源目录；固定样本采样时人工复核，不对用户查询一律排除 |
| 时序分析 | 仅比较真实采集点；每日保留最后一个有效观测 |
| 统计阈值 | 样本数量不足时返回 null 和限制说明，禁止自造 p 值 |

### 5.3 指标计算（实现时写纯函数及单元测试）

- `age_days = (collected_at - created_at).total_seconds()/86400`，对未来/无效创建日期标记异常；不能按今天重新计算旧分析结果。
- `days_since_push = (collected_at - pushed_at).total_seconds()/86400`；缺失为 null。
- `stars_delta = last_observed_stars - first_observed_stars`；仅提供区间两个或更多真实观测时，注明净变化及起止日期。
- `recently_pushed_90d` 在 `pushed_at` 非空且落在 `collected_at` 前 90 天时计算；无 pushed_at 为 unknown。
- `commits_90d`: 必须以窗口 UTC 边界明确表示，统计已完全获取的提交数；若分页缺失返回 null 或部分值并标明 coverage=partial，不能称完整。
- `release_count_365d`: 统计窗口内 GitHub Release 数；未能完整遍历时 coverage partial。
- `issues_closed_90d`: 以关闭时间在窗口内为准；仅看到最近被修改 Issue 的子集时不能称完整关闭数。
- `pr_merged_90d`: 使用 PR `merged_at` 在窗口内判断；部分 PR 分页无法覆盖则标识 partial。
- `Spearman(stars,forks)`: 每一对有效仓库数 n≥统计函数最小有效要求（课程建议 n≥10 才展示研究性结论），有常量输入时系数和 p 值设 null；n、系数、p 值、分组条件一起返回。

所有指标版本在 `metric_version` 中明确保存（例如 `metrics-v1`），后续算法变化需能区分旧结果。

### 5.4 数据质量报告

- 字段缺失率、重复记录数、有效/无效日期、过滤/排除原因统计。
- 固定样本采集的候选数、纳入数、排除数及层级分布必须可追溯。
- `records_total` 指成员规模，`records_analyzable` 指有效分析样本数，两者分开；缺失率分母定义统一。
- 深度数据覆盖按模块标注 complete/partial/not_collected。

## 6. 固定研究样本的科学选择与版本化

- 初始目标为 Python、Java、Rust、TypeScript 每种约 100 个有效软件项目；先做每种 20 个项目的试采样，不应假定最终样本必然满足配额。
- 规则：公开、非 Fork、初始排除 archived，明确软件项目类型；年龄和 Star 区间先定义候选分层，再取样。**不排除长期未推送的仓库**，否则维护停滞指标失真。
- 数据抽样需记录 GitHub search 查询、运行时间、候选数量、`incomplete_results`、项目筛选理由、语言层级、Star 层级、固定随机种子。
- 如果未能完整获取候选总体，只能称“分层配额样本”，不能假称覆盖 GitHub 全体的概率随机抽样，也不能计算所有 GitHub 语言生态份额。
- 生成冻结 dataset：`research-2026-v1`，带 `rules_version`、`frozen_at`、成员列表、每仓库选择理由；个人库 `library-default` 的变动不改变样本。
- 种子数据必须随仓库提供 metadata、来源与导入脚本；网络受限时可以重建本地研究数据，但不得把演示 JSON 当真实采样证据。

## 7. FastAPI 20 个接口的分工与实现次序

具体请求 JSON、枚举、路径与响应结构完全遵循 `03_API接口契约_v1.0.md`，此处只分模块负责与实施顺序。

| 路由文件 | API 编号 | 后端逻辑 |
|---|---|---|
| `main.py`、`system.py` | 01/02 | healthz/系统和配额/Worker 快照 |
| `github.py` | 03/04 | 搜索、解析地址、远程预览（不入库） |
| `library.py` | 05/06/07 | 新增/重复添加/列表/移除成员关系 |
| `repositories.py` | 08/09/10/11 | 仓库资料、任务触发、分析、历史序列 |
| `tasks.py` | 12/13/14 | 任务列表、查询、新任务重试 |
| `datasets.py` | 15 | 研究数据集及版本信息 |
| `analytics.py` | 16/17/18/19 | Dashboard、研究、质量、比较 |
| `exports.py` | 20 | CSV 安全导出 |

所有 JSON 路由应声明 Pydantic `response_model`，响应统一 `{"data":..., "meta":{"request_id":...,"generated_at":...}}`；错误包裹见 API 文档。返回 `204` 时不得附加 JSON；CSV 返回 `text/csv` 字节流（UTF-8，Excel 公式注入防护）。

`/healthz` 测进程存活即可，不在每次 GET 时请求外部 GitHub。`/system/status` 根据 Worker 最近心跳和已有的限流缓存判断，无法确定时返回 unknown/null，不造“运行正常”。

**首版应使用 `/api/v1` 内部 Key 防止本地服务被任意调用**，API/Worker 监听或部署边界需限制访问；无用户登录系统不能作为公网多租户产品开放。

## 8. Worker 设计：状态机与异常恢复

### 8.1 生命周期

```text
queued --[领取并写租约]--> running
                                   | collecting
                                   | cleaning
                                   | analyzing
                                   | persisting
                      ├── 成功 --> succeeded
                      ├── 部分数据可用 --> partial
                      └── 不可用 --> failed

failed/partial --[用户 retry]--> 新建任务 queued（保留旧任务）
```

### 8.2 领取任务的 SQLite 并发安全

- 单 Worker 情况也必须防止意外重复启动：通过租约/实例锁 + SQLite 事务保护领取。
- 使用 `BEGIN IMMEDIATE` 或 SQLAlchemy 等效受控事务，在单个短事务内选出最旧 queued task、更新为 running、写 `lease_owner/lease_until`、commit；**事务结束后**再发外部 GitHub 网络请求。
- Worker heartbeat 定期更新独立 `worker_status` 和运行任务 lease；崩溃/超时任务到期后恢复为 queued 或 failed，重试次数达到最大值后标记 failed。恢复时检查最新成功快照，避免重复写入错误数据。
- 同 `repository_id` 避免同时运行 basic/deep 任务；深度任务会覆盖基础数据需求，初版允许其他任务排队等待。

### 8.3 部分成功与快照写入

- 基础仓库详情成功、Issue/PR 深度失败：仍提交基础有效快照，`task.status=partial`，模块 coverage 分别记录，不删除既有分析。
- 完整 GitHub 请求失败/数据验证失败：该次任务 failed；已有快照及旧分析保留，UI 可展示旧数据并提示更新时间。
- 阶段改变时提交任务状态；最终结果入库与 task 状态更新应在一致性事务中提交，避免 succeeded 但查不到结果。
- 任务完成时间、采集成功时间、GitHub 原始数据时间是不同概念，分别存储。

### 8.4 调度设计

- APScheduler 3.x 只在 Worker 主进程创建一个实例，按天检查已加入个人库及固定研究样本的基础快照；不要在 FastAPI 或 Streamlit 入口自动启动调度器。
- 每日任务应该将符合 TTL 的 repo 入队，不跳过 API 限流；延迟执行比造成不可控 API 请求更好。
- 增量更新策略：basic 每 24h 可检查一次；deep 按需触发，历史事件可设置较长 TTL；**不要承诺秒级实时**。
- 不允许每次进入分析页面就启动完整采集。

## 9. 安全与部署边界

- `GITHUB_TOKEN`, `INTERNAL_API_KEY` 仅在服务端 env 或 secrets；提供 `.env.example` 不含真实值。
- 后端端口本机默认 `127.0.0.1:8000`；前端服务 `8501`；如果外部可访问，使用反向代理认证、TLS、网络 ACL，FastAPI 仅对前端服务器开放。
- 不实现用户账户与数据隔离；系统明示为单人/共享课程演示工作区，禁止宣称多租户安全。
- GitHub API 主机写死或 allowlist；URL 解析不可转发客户端 URL，绝不直接 fetch 任意站点；防止 SSRF。
- Pydantic 校验 `q` 最大长度、合法语言、Star 范围、排序、时间区间、项目对比数 2–5。
- 后端输出 CSV 对以 `=`, `+`, `-`, `@` 开头的文本进行安全处理；应用日志脱敏 Token/API Key/请求头。
- 数据库以目录级权限保护，公开部署不允许文件下载端点访问任意本地路径。
